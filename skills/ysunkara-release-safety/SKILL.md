# Preserve ysunkara.com endpoints

Multiple independent apps share Vercel project `reyash`, repository `ysunkara-27/reyash`, production branch `main`, canonical host `www.ysunkara.com`. The apex redirects to `www`. Only the assembled `dist/` is published; a source directory existing locally does not make it public. The current working directory may be months behind production and contain unrelated uncommitted work.

Repeated endpoint losses have occurred. Hello Flow's directory, build inclusion and slash redirect existed only in an old local checkout; a later GitHub deployment lacked them. Treat the remote production source and the tracked availability contract as the release baseline.

1. Locate the repository and read `AGENTS.md`, `DEPLOYMENT.md`, `vercel.json`, `scripts/build-site.mjs` and `config/production-routes.json`. Inspect Git status and the active production deployment's commit. If the checkout is dirty or behind production, prepare an isolated checkout from the latest `origin/main` and port only this task's changes. Preserve concurrent changes and all current public routes. Do not copy old whole-site configuration over current production.
2. For a new endpoint, commit its source, build inclusion, routing and contract entries together. Keep slash behavior compatible with relative asset URLs. Preserve redirects to Taskpup and Blindspot, Worker proxies, API handlers and unrelated pages. Update the contract for intentional product changes; do not delete entries to silence failures. Retiring an endpoint needs an explicit user request, not a fresh approval for ordinary authorized work.
3. Validate the actual release checkout: run the changed app's relevant checks, `node --test scripts/production-routes.test.mjs`, and the full build command from `vercel.json`. Its final step validates every registered HTML entry, its local script/stylesheet files, and protected routing/API source. New generated apps must be registered. Include new standalone pages and examples of wildcard/API routing in the contract as needed. A missing file or route must fail the release.
4. Use the existing GitHub-to-Vercel integration or the established deployment process; do not introduce another hosting project or alter audience/DNS. Confirm the exact commit became Ready and owns the production domain. Then run `node scripts/production-routes.mjs --live https://www.ysunkara.com`. It checks page identity, local scripts/stylesheets and redirects, catching 404s and HTML fallback responses. Exercise the changed interaction; static checks do not prove app behavior or downstream service health. Probe touched APIs with documented non-mutating requests. If preview protection blocks checks, use authenticated Vercel tooling rather than disabling protection.
5. If production regresses, compare with the previously verified deployment and restore affected paths promptly. Prefer a focused forward fix; a rollback must preserve concurrent newer releases and be followed by the source correction. Do not stop at a successful upload. Report deployed URL, cause/fix, checks and any unresolved failure.

The contract covers registered routes, not every possible API response or future outage. Expand it as endpoints are added. Do not promise absolute uptime or silently create monitoring subscriptions, schedules or third-party services. This workflow does not itself authorize deployment; follow the user's task and existing authorization.
